⚙ Project Overview

Auto-Shop is an event-driven inventory management platform that keeps product stock levels synchronized across multiple sales channels — including physical stores (POS) and online marketplaces such as Mercado Livre and Meta Marketplace.

When a sale is registered on any channel, stock is automatically decremented across all connected listings. Likewise, manual stock adjustments propagate outward to all marketplace listings in near real-time.

Problem it solves

Prevents overselling and manual stock reconciliation across multiple platforms.

Core capability

Real-time bidirectional stock sync between physical POS and online marketplaces.

Extensibility

Microservice architecture allows new marketplaces to be added with minimal impact.

🔌 Microservices

Each service owns a bounded context and communicates asynchronously via RabbitMQ for stock events, and synchronously via REST/HTTP for queries.

1. API Gateway Service

Single entry point for all external traffic. Handles routing, rate limiting, request validation, and forwards requests to internal services.

Kong / Custom TLS termination Rate limiting

2. Auth Service

Issues and validates JWT tokens for internal users. Manages OAuth 2.0 token lifecycle for Mercado Livre and Meta API credentials.

JWT OAuth 2.0 Refresh tokens

3. Inventory Service

Core service. Owns the stock ledger. Exposes endpoints to create/update/query product quantities. Publishes stock.updated events on every change.

MongoDB Publishes events Source of truth

4. Order Service

Receives purchase orders from all channels (POS terminal, marketplace webhooks). Validates, persists the order and emits order.created events that trigger stock deduction.

MongoDB Publishes events Multi-channel

5. Mercado Livre Integration Service

Dedicated adapter for the Mercado Livre API. Receives incoming order webhooks, maps them to internal order schema, and pushes stock updates back to listings when inventory changes.

Webhook receiver ML API v2 OAuth 2.0

6. Meta Marketplace Integration Service

Adapter for Meta Commerce / Facebook Marketplace API. Handles catalog sync, incoming purchase events via webhooks, and outgoing stock updates via Commerce API.

Webhook receiver Meta Commerce API Graph API

7. Product Service

Manages the product catalog: SKUs, descriptions, images, categories, and marketplace listing IDs. Acts as the reference for Inventory Service when resolving product identity.

MongoDB SKU registry Listing mapping

8. Notification Service

Listens for low-stock and out-of-stock events. Delivers alerts via email, push notification, or in-app message. Configurable thresholds per product.

Subscribes events Email / Push Thresholds

9. Reporting Service

Read-only service for dashboards. Aggregates sales by channel, stock history, turnover rates. Reads from MongoDB with aggregation pipelines or a dedicated read replica.

Read-only Analytics Dashboard API

10. POS (Point of Sale) Service

Backend for in-person sales terminals. Processes physical purchases, creates orders in the Order Service, and syncs with Inventory in real-time. Can operate offline with local queue.

Offline-first Local queue Reconciliation

⚠
Recommended MongoDB Indexes Ensure compound indexes on { sku, source } in stock_movements for fast per-SKU history queries. Add a TTL index on sync_logs for automatic cleanup of old entries after 90 days.

🔗 Marketplace Integrations

Mercado Livre

Uses the official Mercado Libre API v2 with OAuth 2.0 authorization code flow. Key operations:

  • Receive order webhooks (/notifications)
  • Update listing stock via PUT /items/{id}
  • Pause listing when stock reaches 0
  • Token auto-refresh every 6 hours
OAuth 2.0 Webhooks Rate: 3000 req/min

Meta Marketplace

Uses the Meta Commerce Platform API (Facebook Graph API). Key operations:

  • Manage catalog via /catalog/{id}/items
  • Receive purchase events via Webhooks
  • Update inventory via POST /catalog_item_updates
  • Handle checkout_update webhook for pending orders
Graph API Webhooks Catalog API
ℹ
Idempotency is critical Both marketplaces can deliver duplicate webhook events. Always check stock_deducted: true on the order before processing. Use the external order ID as an idempotency key when inserting into the orders collection.

↻ Key Data Flows

Online Sale (Mercado Livre / Meta)

1
Webhook received

Marketplace posts an order notification to the respective Integration Service endpoint.

2
Signature validation

Integration Service validates the webhook HMAC signature and fetches full order details from the marketplace API.

3
Order normalization

Marketplace-specific order schema is mapped to the internal Order schema and sent to the Order Service via REST POST.

4
Order persisted & event emitted

Order Service saves the order to MongoDB and publishes an order.created event to RabbitMQ.

5
Stock deducted

Inventory Service consumes the event, deducts stock, updates stock_levels, appends to stock_movements ledger, and emits stock.updated.

6
Marketplace sync

Both Integration Services consume stock.updated and push the new quantity to their respective marketplace listing APIs.

7
Low-stock check

If new quantity falls below threshold, Inventory Service additionally emits stock.low, triggering a notification via the Notification Service.

In-Person Sale (POS Terminal)

1
Sale registered at POS

Cashier scans products; POS app calls the POS Service with a sale payload.

2
Order created

POS Service forwards to Order Service with source: "pos". Same flow from step 4 above applies.

3
Offline resilience

If the POS terminal is offline, sales are queued locally (SQLite) and synced when connectivity is restored — preventing double-counting via idempotency keys.

☁ Infrastructure & DevOps

Repository Structure

Monorepo (recommended) using pnpm workspaces or Turborepo. Each service lives in apps/<service-name>, shared types in packages/shared.

Local Development

Single docker-compose.yml at the root spins up all services, MongoDB, Redis, and RabbitMQ with one command: docker compose up.

CI/CD Pipeline

GitHub Actions runs lint → tests → build → Docker image push → K8s rolling deploy per service. Each service deploys independently.

Security

Secrets managed via Kubernetes Secrets or HashiCorp Vault. OAuth tokens encrypted at rest in MongoDB. All traffic inside the cluster over mTLS.
